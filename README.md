# UAV-AAS connector: experiment data

Raw measurements and analysis scripts for the evaluation of a connector that
maps MAVLink telemetry from a UAV to Asset Administration Shell (AAS)
properties and exports them over OPC UA and MQTT. The connector is compared
against a naive Python gateway and against Eclipse BaSyx with two bridge
variants.

## Testbed

Two hosts on the same LAN:

- **Edge device:** Raspberry Pi 5 (4 GB), Raspberry Pi OS 64-bit. Runs the
  system under test in Docker (`network_mode: host`) and the resource monitor
  sidecar.
- **Workstation:** runs the MAVLink replay, the MQTT broker (Mosquitto), the
  OPC UA server (port 4841) and the MQTT receivers.

Telemetry goes from the workstation to the Pi over UDP (port 14550), and the
Pi's AAS updates come back to the workstation. Dispatch and arrival timestamps
are both taken on the workstation, so latency covers the full round trip and
no clock synchronisation between hosts is needed.

### Workload

Each run replays a synthetic MAVLink `.tlog` for 900 s at an aggregate rate
of 10, 50 or 200 messages/s (31 message types). The logs are in `inputs/`
and can be regenerated byte-for-byte with:

```
python scripts/replay/synth.py --hz 10 --duration 900 --out synth_10hz_15min.tlog
```

`replay.py` writes an increasing counter into `LOCAL_POSITION_NED.x` and logs
it as `Seq`. Every arrival of that property can therefore be matched to the
exact message that produced it.

| Rate | MAVLink messages dispatched |
| --- | --- |
| 10 Hz | 9,012 |
| 50 Hz | 45,011 |
| 200 Hz | 180,011 |

Runs were executed one at a time.

### Systems

| Directory | System | Protocols | Components on the Pi |
| --- | --- | --- | --- |
| `data/connector` | Proposed connector (Go) | OPC UA, MQTT, both at once | 1 container |
| `data/baseline` | Naive Python gateway, sequential and blocking | OPC UA, MQTT | 1 container |
| `data/basyx_basic` | Eclipse BaSyx + bridge sending one PATCH per property | MQTT | BaSyx AAS environment (JVM) + Python bridge |
| `data/basyx_batched` | Eclipse BaSyx + bridge sending one PATCH per submodel, pipelined | MQTT | BaSyx AAS environment (JVM) + Python bridge |

BaSyx has no OPC UA interface in this setup (REST plus MQTT eventing only).

## Layout

```
data/        19 runs used in the paper, one directory per run
excluded/    runs that were recorded but not used (see below)
inputs/      synthetic .tlog files replayed in every run
scripts/
  replay/            replay.py (dispatcher), synth.py (tlog generator)
  receivers/         mqtt_receiver.py, basyx_mqtt_receiver.py, opcua_server.py, nodeset, mosquitto.conf
  resource_monitor/  Docker stats sidecar
  analysis/          latency, delivery and resource analysis
  unpack.sh          decompresses the data and checks SHA256SUMS
SHA256SUMS   checksums of the uncompressed files
```

Run directories are named `<protocol>_<rate>_<system>`. Files larger than
1 MB are stored as `.xz`. Run `scripts/unpack.sh` before using the scripts,
since they read plain CSV.

| File | Recorded on | Columns |
| --- | --- | --- |

| `naive_baseline*_metrics.csv`, `basyx_baseline_bridge_metrics.csv` | Pi, Python gateway and naive bridge | `System_Time, Message_Type, MAVLink_Seq, Dropped_Since_Last, Queue_Wait_ms, Processing_Latency_ms, CPU_Percent, Memory_MB, Write_Success, Error` |

| `basyx_batched_flush_metrics.csv` | Pi, batched bridge | `System_Time, Submodel, Properties_In_Payload, Flush_Latency_ms, Coalescing_Lag_ms, CPU_Percent, Memory_MB, Write_Success, Error` |
| `*.png` | | charts produced by the analysis scripts |

`latency_*.log` records a timestamp at each internal stage of the connector
(`ADAPTER`, `CORE`, `MQTT_SENDING`/`MQTT_SENT`,
`OPCUA_SENDING`/`OPCUA_SENT`), and `TraceID_ns` groups all the
properties derived from one MAVLink message.

## Metrics

- **End-to-end latency:** `Arrival_Timestamp_Ms - Dispatch_Timestamp_Ms` for
  each `Seq` value, both taken on the workstation clock
  (`latency-calculate.py`).
- **Delivery ratio:** matched `Seq` values divided by unique dispatched `Seq`
  values.
- **CPU and memory:** Docker Engine stats for the container under test,
  computed the same way as `docker stats`. The sidecar keeps polling for a
  short time after a run ends, so `resource_analyzer.py` drops samples with
  zero memory. With `--align-to` it also drops any samples outside the run's
  dispatch window. For BaSyx, the JVM and the bridge are measured separately
  and added together.

## Reproducing the numbers

Tested with Python 3.14. Run commands from the repository root, since the
analysis scripts write their charts to the current directory.

```
python3 -m venv .venv && . .venv/bin/activate
pip install -r scripts/requirements.txt
./scripts/unpack.sh
```

End-to-end latency and delivery ratio:

```
R=data/connector/opcua_10hz_connector
python scripts/analysis/latency-calculate.py $R/dispatch_connector_opcua_10hz.csv $R/opcua_server_log4841_20260815_085404.csv
```

The BaSyx receiver logs properties as `LocalPositionNED.X` instead of
`LocalPositionNED/X`, so add `--seq-node-suffix LocalPositionNED.X` for
`basyx_basic` and `basyx_batched` runs.

CPU and memory:

```
python scripts/analysis/resource_analyzer.py $R/uav-aas-connector_20260815_115413.csv --align-to $R/latency_20260815_115413.log
```

For the Python gateway, align to `naive_baseline*_metrics.csv`. For BaSyx,
align to `basyx_baseline_bridge_metrics.csv` (naive) or
`basyx_batched_ingestion_metrics.csv` (batched), and run the analyzer once on
`basyx-bridge_*.csv` and once on `basyx-aas-env_*.csv`.

Other scripts in `scripts/analysis/`:

- `latency_analyzer.py`, `message_latency_analyzer.py`: connector-internal
  latency per pipeline stage, from `latency_*.log`.
- `baseline_latency_analyzer.py`: per-message processing latency reported
  by the Python gateway.
- `message_loss_analyzer.py`, `dropped_traffic_analyzer.py`: dropped and
  coalesced updates.

## Collecting new data

On the workstation:

```
mosquitto -c scripts/receivers/mosquitto.conf
python scripts/receivers/opcua_server.py scripts/receivers/quad_op.nodeset.xml 4841
python scripts/receivers/mqtt_receiver.py --log mqtt_received_log.csv     # or basyx_mqtt_receiver.py
python scripts/replay/replay.py inputs/synth_50hz_15min.tlog --ip <pi-address> --log dispatch.csv
```

On the Pi, start the system under test and the sidecar from
`scripts/resource_monitor/` with `TARGET_CONTAINER=<container name>`.
